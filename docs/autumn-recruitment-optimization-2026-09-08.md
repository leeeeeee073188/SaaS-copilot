## 1. 推荐定位与取舍

保留 FastAPI + Vue + Redis + ChromaDB + 原生异步 Agent 的架构。将项目聚焦为：**面向 SaaS 客户交付与续费准备的证据驱动分析助手**。技术主线是“复杂问题按需协作、结论可追溯、长期记忆不串客户、优化收益可复现”。

简历最值得强调的三个专题：

1. **按需多 Agent**：简单问题直接回答，复合问题才进行有预算的主辅协作，用单 Agent 对照证明协作价值。
2. **证据闭环 RAG**：客户、时间、文档版本约束进入召回，结论能点开来源，缺少证据时明确待补信息。
3. **实际用户链路评测**：同一个处理入口覆盖记忆、检索、工具和生成，报告任务完成率、证据指标、成本与延迟。

分级记忆和意图识别作为上述主线的支撑，不把每个模块都包装成算法创新。现有模块足够多，短板主要在业务数据、边界正确性与实验可信度。Anthropic 的工程经验明确区分路由、并行工作流和自主 Agent；本项目适合受控工作流加局部工具决策，而不是开放式自治系统。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

### 2.1 应优先处理的小问题

- **压缩后消息顺序**：`MemoryManager._compress` 对 `reversed(keep)` 做 LPUSH，读取又 reversed；与常规逐条 LPUSH 的顺序不一致。对时间顺序 `[m1,m2,m3]`，此写法存成 `[m1,m2,m3]`，读回变 `[m3,m2,m1]`。先补真实压缩路径的顺序回归测试再修正。
- **压缩并发与失败丢信息**：读取旧列表、摘要、delete、重建之间没有会话级并发保护；摘要失败仍会继续裁剪，情景持久化内部异常也只记录日志。最小单进程方案让“同会话添加+压缩”使用同一锁，摘要/归档成功后才裁剪；多 worker 则需要 Redis 原子化/版本检查，不能把进程内锁说成分布式安全。长期方案应以消息 ID 或序列水位只裁剪已归档前缀。
- **延迟口径**：`/chat` 返回 `result.latency_ms`，计时位于编排器，漏掉前置记忆、意图和预取，以及后置写记忆；并行分支还有独立计时。应在请求入口到返回边界计服务端总时长，并从客户端测 HTTP 完整延迟。
- **距离口径**：KB 未指定 `hnsw:space`，却把 `1-dist` 标成相似度。固定依赖 Chroma 0.5.23 的默认是 L2；最小修正是保留原始 distance 并说明越小越近。不要把它当正确率或跨模型通用阈值。换 cosine 或 embedding 时新建版本 collection 并重建索引，不直接修改旧向量语义。[Chroma 0.5.23 源码](https://github.com/chroma-core/chroma/blob/0.5.23/chromadb/segment/impl/vector/hnsw_params.py)
- **降级不是证据**：KB fallback 返回说明性条目；聚合后的 success 不足以说明查到了有效知识。预取与 tool-use 都应排除 `fallback=true` 项，返回 `retrieval_status=degraded/empty/ok`，不可只显示 RAG 已使用。
- **实例路由表述**：当前每类仅一个实例，`_best_agent` 的性能分数没有同类竞争选择空间。不要声称已经证明自适应负载均衡收益。
- **MCP 表述**：当前 `mcp/tool_manager.py` 是本地 handler 注册与调用，依赖及执行路径未见 MCP 会话、传输与协议握手。可写“工具治理层”，不能写成标准 MCP 服务互通。真实 MCP 强调 host/client/server 和协议交互；若目标岗位特别看重 MCP，后续给只读知识搜索加薄适配，并演示真实 client 调用。[MCP 架构规范](https://modelcontextprotocol.io/specification/2025-06-18/architecture)

当前 `wiki/简历项目描述.md` 中“编排器评测验证记忆读取”等说法需要随实施修订；意图 embedding、MCP、性能路由也应使用上述准确口径。已有字段级画像更新无需重新实现。

## 3. 完善业务背景：一条可演示的客户问题链

沿用已接受的 ADR 0001：FlowForge Cloud 是虚构的数据集成 SaaS，使用者是内部交付、技术支持、客户成功与续费运营人员。产品输出分析和建议，不自动执行生产操作。这与现有角色和工具一致。

### 3.1 核心用户任务

用户在同一客户项目中遇到“集成故障影响上线，使用量下降，续费准备受阻”，目前需要串查排障手册、实施记录、事件单、使用快照和套餐条款。SaaS Copilot 将其变为：**定位事实 → 解释影响 → 列出待验证项 → 输出有优先级的下一步**。价值假设是减少资料切换与证据遗漏，而不是承诺提升实际续费率。

| 用户任务 | 必要输入 | 输出与完成标准 | 哪个能力有必要 |
|---|---|---|---|
| 查 Webhook 重试规则 | 产品版本、适用环境 | 引用当前有效手册，不牵扯续费结论 | 单 Agent + RAG |
| 判断上线阻塞 | 项目、验收计划、故障记录 | 已满足/未满足/未知的验收项，故障证据 | Support 主、Delivery 辅 |
| 准备续费风险摘要 | 合同时间、采用数据、未闭环问题 | 区分事实、假设与缺口；不能把使用下降直接等同流失 | Renewal 主、按需 Support/Success |
| 追问“现在恢复了吗” | 同客户的更新事件快照 | 新事实覆盖旧结论，说明截至时间 | 时间过滤 + 记忆纠正 |
| 切到另一客户分析 | 明确新 project_id | 历史偏好可复用，前一个客户故障不能作为事实 | 项目范围隔离 |

### 3.2 合成业务材料设计

首轮建议制作 **3 个客户项目、30–50 篇材料**，作为演示和开发集。这是待制作的目标数量，当前仓库没有这些资料；README 所说的 `data/demo_docs` 目录在审阅时也未找到。材料全部注明“合成”，不声称来自真实企业。

推荐构成：产品与排障手册 8–10 篇、项目和验收记录 6–8 篇、事件及后续更新 8–12 篇、用量快照 4–8 篇、服务计划/续费准备记录 4–8 篇。故意包含同错误码不同原因、过期手册、矛盾记录、缺失数据和无关文档，避免只有五段规则时近乎必中的虚假效果。

每份材料标记 `source_id / project_id（或 global）/ doc_type / version / valid_from / valid_to / updated_at / source_title`。这些是拟新增的业务来源信息，当前上传模型和 KB 不会自动保留它们，必须贯通导入模型→chunk metadata→过滤→检索结果→引用。初期也可将关键字段写进正文便于人工演示，但正文标签不能替代程序过滤。

统一演示案例（以下都是拟造数据）：

> 截至 2026-09-08，项目 `proj_aurora` 计划 9 月 15 日上线，服务计划 10 月 31 日到期。事件 `INC-042` 从 9 月 7 日起记录 Webhook 401，最近 7 天任务成功率 92%，前 7 天 99%。手册说明 401 有多种认证原因，当前缺少密钥版本证据。

正确回答应引用事件和指标，指出上线验收可能受影响，列出密钥版本/签名检查；不能断言根因、承诺恢复时间或推断一定不续费。接着提供 9 月 9 日“401 已恢复，积压仍在”的更新，再问上线风险是否解除，检验时间与冲突处理。

最终输出固定为：**结论（含截至时间）/已知事实与引用/假设和缺口/按优先级排序的行动建议**。这些区块先用 prompt + 引用字段实现；只在确需前端消费时增加完整结构化答案协议。

## 4. 意图识别：减少不必要模型调用，保留上下文能力

借鉴选择性路由思想，而不训练新分类器。RouteLLM 研究的是强弱模型选择，不是本项目的业务意图分类；能借鉴成本与质量的权衡实验，不能直接套用其阈值或声称复现算法。来源和开源实现见配套调研笔记。

最小链路：`命中含历史版本的缓存 → 极少量无歧义规则短路 → 原有 LLM + 规则融合 → 缺信息则澄清 → 业务路由`。

1. 短路先只覆盖纯问候和明确的单一模板问法；含否定、多个领域、代词或风险升级时继续 LLM。普通“Webhook”关键词不能代表高置信度。
2. 保留 19 标签给细分诊断；优先评估六组路由与主 Agent 选对率，别为了增加类别数继续细分。
3. 可给识别结果加 `domains[] / missing_fields[]`，辅助路由由“当前任务确需的领域”决定；这是小扩展，不强制重写所有 IntentCategory。
4. `confidence` 暂叫路由分数；在独立开发集上画覆盖率—错误率曲线，选择短路/澄清阈值。LLM 自报置信度、向量距离、关键词分数不可直接解释成同一种概率。
5. 模板学习或规则更新时清缓存或把规则版本放进 key；给中文近义表达、否定和多轮指代增加反例。

验收：规则短路准确率、短路覆盖率、低置信度澄清率、六组 Macro-F1、主 Agent accuracy、每请求意图阶段 LLM 次数。先用离线标注验证“省调用且误路由不增加”，再扩短路范围。

## 5. 多 Agent：用有边界的协作替代关键词扇出

LangGraph 的状态、条件边和并行汇合可以作为设计参照；当前 `Request / RoutingDecision / AgentResponse / ResponseComposer` 已具有可复用结构，无需迁移依赖。保留确定性轮数和预算即可，具体来源见配套笔记。

建议契约：

```text
Request: message + project_id? + as_of? + history + request_id
RoutingDecision: primary_agent + supporting_agents(<=2) + reason
SpecialistResult: status + findings + evidence_ids + uncertainties
Final: conclusion + citations + missing_info + suggested_actions
```

实施边界：

- 简单事实问答只调用一个 Agent。复合问题需要两个以上独立分析目标才并行；“暂不考虑续费”不派 Renewal。
- 同一请求预取的证据作为共享只读上下文，工具查询仍按完整参数缓存；子 Agent 按领域检索缺口，不把同一问题各改写三遍。先请求内去重，后考虑跨请求缓存。
- 对 Agent 执行、检索、Composer 分别设置 timeout，同时设请求总 deadline。并发 semaphore 是共享限流，不是在每个请求里各建一个。
- 默认最大三个专家含主 Agent、最多三轮工具交互可作为起点；轮数之外还限制工具总次数。超时和失败以 `partial/degraded` 返回，不把成功返回一段文字等同任务完成。
- Composer 只使用带来源的有效结论；不同专家冲突时展示两组来源和待验证问题。主 Agent 失败时明确哪个专家结果被采用，避免结果字段仍指向未完成的主领域。
- 现有 `_last_tools_used/_last_tool_traces` 是实例字段：后续修改时把请求状态放回局部结果对象，降低共享实例在异常/并发路径中串轨迹风险；是否已发生需并发回归验证，不能仅凭字段就宣称线上故障。

关键消融：同模型、同证据、同样总输出预算下，比较“单一通用 Agent”“现有关键词并行”“受控主辅协作”。分简单集与复合集报告任务完成率和成本。多 Agent 只有在复杂任务收益抵消额外开销时才保留；不能拿更多 token 的结果证明架构本身优越。

## 6. RAG：先可信，再提高召回

### 6.1 必做的小改动

1. 检索返回真实 `chunk_id/source_id/version`，按 chunk_id 去重；兼容旧文档时才用稳定的 title+content 哈希，不包含动态 score。
2. 请求显式 project_id，并将过滤传到每次预取、改写召回和 tool-use；允许 `global` 产品手册与当前项目材料，过滤后再召回。不要先全库取 Top-K 再过滤，那会漏掉本应被召回的项目文档。
3. 添加有效期/更新时间，过期文件默认不作为现状依据；项目事实和产品规则采用不同权威优先级。相互冲突时展示冲突，不只取时间最新的一条。
4. 前端引用展示原文、版本、时间；程序只允许引用当前证据集合中的 ID。ID 存在不代表结论被证据支持，后者由评测和人工抽审判断。
5. 重排返回索引需校验整数、范围和重复，异常保留原候选；跟踪 rerank 实际执行/成功状态，不能 fallback 也记“已重排”。
6. 同一文档更新需要明确旧版本保留或失效，内容哈希用全文，不能依赖 chunk 前 50 字；缓存 key 包含 query、top_k、过滤条件、知识版本和重排版本。

注意范围：project_id 过滤是本演示的数据语义隔离，客户端可自报 user_id 并不构成认证。现 ADR 不要求 RBAC；若未来用于真实多租户，租户和权限必须来自可信身份上下文，这不在本次最小项目改动内。

### 6.2 有证据再加的召回优化

建议在 KB 后增加轻量 BM25 词法召回，与原 Chroma dense 召回通过 RRF 合并：`score(d)=sum(1/(k+rank_i(d)))`。`k=60`、每路 Top-10、合并后 Top-5 仅是开发起点，需开发集调参。中文采用固定分词或字符 n-gram，错误码/项目编号/接口路径保留完整 token。索引随知识版本构建，两个通道使用相同项目和版本过滤。

采用 BM25 的业务理由是错误码、连接器名和标识符精确匹配，采用 dense 的理由是中文近义表达，两路互补。LlamaIndex 的融合检索、RAGFlow 的检索管线可参考设计，不迁移整个平台。BGE-M3 是中文多语言向量候选；先与当前默认模型对照，硬件与速度允许再替换。更换 embedding 必须对知识与记忆 collection 分别评估并重建，不能新旧混用。[LlamaIndex 融合检索示例（历史版本，用于机制参考）](https://docs.llamaindex.ai/en/v0.10.19/examples/low_level/fusion_retriever.html)、[FlagEmbedding 官方模型表](https://github.com/FlagOpen/FlagEmbedding/blob/master/README.md)

查询改写只在多意图、指代或召回不足时触发，保留原 query，强制保留项目/错误码/版本。LLM rerank 与专用 reranker 只做候选比较，不默认增加一个模型服务。初期保留现有 LLM 重排即可，但衡量其真正增益。

不优先做 GraphRAG、复杂知识图谱或训练式 Self-RAG：当前任务是局部事实和少量跨域分析，先证明普通检索做不好的实例。可以借鉴 Self-RAG 的“需要检索/证据是否支持”检查思想，但 prompt 检查并不等于复现其训练方法。[Self-RAG 论文](https://arxiv.org/abs/2310.11511)

## 7. 分级记忆：明确哪些信息可以长期相信

| 层级 | 保存内容 | 作用域 | 写入/读取规则 |
|---|---|---|---|
| 工作记忆 | 当前问题、项目、最新纠正、待补字段、最近对话 | user + conversation，携带 current project | 保留现 Redis，控制预算；当前明确输入优先 |
| 情景记忆 | 某客户问题的摘要、当时证据引用、未决项 | user + project，附时间/来源 | 压缩成功后写；按项目与时间过滤，过时结论不当现状 |
| 长期画像 | 回答偏好、用户明确确认的稳定信息 | user | 复用现 add/replace/remove；偏好可跨项目，客户瞬时状态不进入全局偏好 |
| 知识库（非用户记忆） | 产品规则、版本化项目事实快照 | global 或 project | 来源和版本控制；不能由助手自己的回答自动写为权威事实 |

最小补强顺序：先修压缩顺序与失败裁剪，再做总摘要预算，再做项目过滤和过期字段读取。`expires_at` 有字段但没有行为不算遗忘机制。若采用时间衰减，要区分偏好与故障状态，不给所有知识一个相同半衰期。

压缩摘要建议包含“已确认事实 / 纠正记录 / 待验证 / 引用 ID”，新旧摘要合并成有上限摘要，而不是不断追加。LLM 没有可用 tokenizer 时可用保守字符预算并明确是近似值；最终成本取 API usage。画像仅在明确偏好/纠正或累计新增信息时异步更新，不是每轮都调用同一个大模型；任务应被追踪、在关闭时收尾。

MemGPT 借鉴分层与受控记忆操作，Mem0 借鉴事实提取和合并；当前已有字段协议，不再引入整套记忆服务。这两项详见调研来源。LongMemEval 可借鉴时间推理、更新、跨会话和拒答的测试分类，不能将本地小型用例成绩称为 LongMemEval 官方榜单结果。[LongMemEval 官方仓库](https://github.com/xiaowu0162/longmemeval)

## 8. 评测链路：从“回答好看”到“能证实优化”

### 8.1 两层入口

保留 IntentEvaluator 和 orchestrator 单元级评测，明确命名为组件测试。把 `/chat` 核心逻辑抽成薄 `ChatService.handle()`（或等效函数），供 API 和任务评测复用，参数注入现有 memory/orchestrator/tool manager。它负责同一条记忆读写、识别、预取、生成和轨迹链路；HTTP 冒烟测试另外检查序列化和路由，不将 service 测试等同 HTTP 测试。

评测使用独立 Redis key 前缀、Chroma collection 和 eval_run_id；多轮复用隔离会话，跨用例不共享画像和缓存。准备金标文档、客户快照和预置记忆。禁止评测污染日常演示用户或把金标答案作为生成上下文。

### 8.2 建议数据规模与划分

最低可信起点：约 **120 条意图问题 + 60 条带来源的业务任务**，其中至少 15 个任务是多轮序列；这些数字是待建立的计划，不是现有资产。资源允许时扩到 200–300 条问题。对 19 个细类，120 条样本不足以支撑稳定细类成绩，优先报告六组与置信区间，并补齐每类样本。

按项目、文档主题或对话模板组划分开发集与冻结测试集，例如 40%/60%；同模板的改写不跨集合，长期记忆测试可单设时间留出。每条记录：case_id、问题/turns、project_id、as_of、期望领域、gold_source_ids、必要事实、禁止断言、是否可答、预置记忆。人工校正金标；可让模型扩写初稿，但不能直接拿生成器的答案当真值。

### 8.3 指标口径

| 层级 | 指标及分母 | 要回答的问题 |
|---|---|---|
| 意图与路由 | 六组 Macro-F1、主 Agent 正确率；短路错误数/短路总数和短路数/总数 | 省调用是否增加误分流？ |
| 检索 | Recall@5（每条 gold 证据召回比例后宏平均）、MRR@5；按同一 source 或 chunk 粒度标注 | 证据有没有被找到？ |
| 引用 | 有效引用 ID 数/引用 ID 数；支持结论的引用数/人工审查引用数；必要事实有来源的覆盖率 | 引用是否存在、是否真正支持？ |
| 任务 | 必要事实和下一步满足且无禁止断言的 case 数/全部 case 数；无答案集正确澄清/拒答率 | 业务任务是否完成？不能靠四维均分掩盖关键错误 |
| 记忆 | 最新纠正采用率、跨会话事实召回率、过期事实误用率、跨项目泄漏例数 | 是否记对、更新、隔离？ |
| 工程 | 客户端 p50/p95、各阶段时长、API usage tokens/请求、模型调用数、工具失败/降级率 | 质量提高花了多少时间与成本？ |

无 gold 证据的不可答任务不进入 Recall 分母，单独计算正确拒答。任务失败、超时、Judge 失败均应展示数量；Judge 失败不计成中性 0.5 混入质量均分。Ragas 提供检索与回答维度划分思路，但其分数不等同业务完成率。Judge 看到实际候选证据、金标必要事实与待评回复；模型身份和方案名称对 Judge 隐藏。抽查至少 20 条（或小集的约 20%）校准评分；同源模型偏差仍需披露。

### 8.4 最值得做的五组消融

| 实验 | 对照 | 预期检验（不是结果） |
|---|---|---|
| 意图 | 现有融合 vs 高精度短路 + 原路径 | 模型调用减少，路由质量不明显退化 |
| RAG | dense vs dense+BM25/RRF；再单独开关重排 | 标识符/错误码子集召回收益与延迟成本 |
| 编排 | 单 Agent vs 现有并行 vs 受控并行 | 复合任务收益，简单任务不浪费 |
| 记忆 | 最近窗口 vs 当前分层 vs 修正后分层 | 更新、时间和隔离正确性，不只测“记得名字” |
| 全链路 | 当前基线 vs 最终组合 | 端到端任务质量、成本与延迟共同变化 |

固定模型 ID、temperature、prompt/skill/知识/embedding/数据版本与 git SHA；分别报告冷热缓存，所有配置用同一份冻结用例。对小样本或随机生成可做三轮配对运行并报告均值、范围/置信区间，不能只有最好一次。p95 要报告请求数、并发数和环境，不从五次调用推高并发能力。

报告按 run_id 追加保存，golden baseline 只在主动接受后更新。回归阈值明确“百分点”还是“相对百分比”，不能只写下降 5%。质量指标、失败率和成本各设门槛，单一平均分不能自动批准版本。

## 9. 最小改动排期与停止条件

估算按一名熟悉现有项目的开发者，包含联调、不包含大规模人工标注。行数是人工修改/新增运行代码的粗估，非验收指标；测试、数据与文档另计。各阶段可以独立停止，不要求为投递全部完成。

### 10.1 当前可用的诚实简历表述

> SaaS Copilot｜SaaS 客户交付与运营分析助手（个人项目、合成业务场景）。基于 Vue、FastAPI、Redis 和 ChromaDB，构建意图驱动的主辅 Agent 路由、真实工具调用及复合问题并行分析；实现规则敏感问题预取与按需 RAG、会话压缩和字段级用户画像更新，提供工具轨迹和编排器级单多轮评测。

### 10.2 实施和实测后的三条 bullet 模板

> - 面向客户上线阻塞与续费准备场景，实现带来源引用的交付/支持/运营主辅分析；通过受控并行和工具预算，将复合任务完成率从 `[A]` 提升到 `[B]`，简单任务平均模型调用 `[C]` 次（冻结测试集 `[N]` 条）。
> - 构建带项目与版本约束的知识检索，结合 `[实际采用的召回方法]` 与 chunk 级引用；证据 Recall@5 `[R]`、引用支持率 `[S]`，保留无答案澄清与检索降级路径。

### 10.3 八个可以深挖的问题

1. **为什么不直接一个大模型？** 展示同模型同证据的单 Agent 对照，只在独立跨域任务上保留协作。
2. **为什么不用 LangGraph？** 已有状态和路由结构满足短任务；持久化恢复/人工中断成为需求时再迁移，理解概念但不为关键词换框架。
3. **置信度 0.8 是什么？** 当前是融合/规则分数，非概率；以开发集覆盖率—错误率选择阈值。
4. **引用就能解决幻觉吗？** 不能，引用存在性可程序检查，支持关系还要证据评测与抽查。
5. **Redis 和 Chroma 为什么都要？** 当前窗口按会话读写、跨会话语义召回是不同访问方式；画像本身可 KV，沿用 Chroma 是减少迁移而非必须向量化。
6. **记忆与知识冲突怎么办？** 用户刚纠正的当前上下文、版本化事实与旧摘要有不同权威性；旧回答不能变成事实来源。
7. **怎么证明 p95 和成本可靠？** 给出请求边界、缓存、并发、模型版本、样本数和失败统计，不把编排器计时当完整耗时。
8. **最大的失败案例是什么？** 演示过期故障记忆、否定关键词误扇出或降级结果误当证据，以及对应小修复与回归用例。

### 10.4 演示顺序

先问一条手册事实（单 Agent、展开引用），再问 `proj_aurora` 的上线+续费复合问题（主辅协作和缺口），再提供事件更新检验旧记忆纠正，最后切到另一个客户检验隔离。结束展示同一测试集的对照报告，说明哪项优化没有收益而被关闭。比展示一张包含十几个框架 Logo 的架构图更能证明工程判断。

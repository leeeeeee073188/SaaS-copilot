调研日期：2026-09-08。本文仅提供外部证据和最小借鉴建议，不代表仓库已实现这些能力，也不代表完成论文复现。论文机制依据作者公开摘要；涉及具体工程实现时另列官方文档或源码。所有收益数字均需在本项目固定数据集上重新实测。

## 核心判断

适合小型 SaaS 内部运营助手的路线，是用明确的业务任务、受控执行、引用证据与回归评测组成闭环，再按失败案例逐步增加复杂度。多 Agent 的价值应来自不同信息源或工具权限的分工；同一问题让多个角色重复回答，不足以证明协作价值。这个取舍与 Anthropic 的简化优先原则一致。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

## 13 组核心来源

### 1. 意图识别需要单独评测域外输入

- **来源事实**：Larson 等，EMNLP-IJCNLP 2019，提出包含 150 个意图、10 个领域和域外查询的数据集；域内分类良好不意味着能可靠识别域外问题。[An Evaluation Dataset for Intent Classification and Out-of-Scope Prediction](https://arxiv.org/abs/1909.02027)
- **最小借鉴（设计建议）**：现有意图标签之外，增加 `clarify` / `unsupported` 处理分支；测试集中加入“缺客户名”“跨任务复合问句”“无关闲聊”“看似业务词汇但实际无支持工具”等样本。分别报告域内 macro-F1、域外误接收率、澄清后完成率。
- **边界**：不用直接训练该英文数据集，也不能把 LLM 自报的 confidence 当校准后的概率。阈值必须在独立开发集调节，测试集只用于最终报告。

### 2. RouteLLM：质量—成本路由，而非业务意图分类

- **来源事实**：RouteLLM 使用偏好数据学习在强、弱模型之间选择，以权衡成本与回答质量。[RouteLLM: Learning to Route LLMs with Preference Data](https://arxiv.org/abs/2406.18665)
- **最小借鉴（设计建议）**：借鉴“固定质量约束下统计调用成本”的实验方法。先对简单业务路由采用规则或便宜模型，对歧义、复合任务升级；比较全量强模型、全量便宜模型、分级策略。
- **边界**：模型选择与意图识别是不同问题；几个规则分支不能写成“复现 RouteLLM”。论文成本收益不能移植到本项目。

### 3. Anthropic：区分 workflow 与 agent

- **来源事实**：预定义代码路径属于 workflow；模型动态决定执行过程属于 agent。官方给出 routing、parallelization、orchestrator-workers 等组合模式，并要求按实测收益增加复杂度。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)
- **最小借鉴（设计建议）**：意图 → 受控分支；知识问答直接检索，查询类直接工具调用，仅复合运营任务进入编排。把复杂场景拆成“查业务事实”“查 SOP”“汇总建议”三个有清晰输入输出的职责。
- **边界**：确定性 DAG 可以是优秀的 Agent 应用工程，但不能宣称实现了完全自主规划。

### 4. Anthropic 多 Agent 研究系统：并行有适用条件

- **来源事实**：官方研究系统使用主 Agent 分解研究方向并并行委派；特别强调职责划分、预算、检查点和失败恢复，并披露该系统多 Agent 的 token 消耗显著高于普通聊天。[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)
- **最小借鉴（设计建议）**：只在“账户使用情况 + 续费 SOP + 历史行动”相互独立的信息收集阶段并行；限制分支数、超时和工具预算，统一结果协议，失败分支返回结构化错误后再汇总。
- **边界**：研究场景收益不等于运营场景收益；不引用其性能数字充当自己的成果。两次并行 LLM 调用也不自动构成有价值的多 Agent 系统。

### 5. LangGraph：状态、检查点与恢复

- **来源事实**：LangGraph 提供有状态编排、持久化、人机协同和调试能力；持久化以线程和检查点组织图状态。[官方仓库](https://github.com/langchain-ai/langgraph)、[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)
- **最小借鉴（设计建议）**：保留项目现有编排框架，明确 state schema、分支输出、终止条件、错误状态与 request ID。只有真实存在中断恢复需求时才引入持久化 checkpointer。
- **边界**：检查点不等于外部写操作的 exactly-once；写工具仍需业务幂等键。已有图结构时无需为了简历换框架。

### 6. Qdrant：稀疏/稠密融合与多阶段检索

- **来源事实**：官方文档展示分别召回稀疏、稠密结果，再用 RRF 按排名融合，也支持多阶段检索。[Hybrid Queries](https://qdrant.tech/documentation/search/hybrid-queries/)
- **最小借鉴（设计建议）**：在现有检索器外增加词法召回与 RRF，保留现有向量库；先做租户/文档状态过滤，再融合、去重、重排。产品名称、错误码、套餐代码适合用作词法召回测试样本。
- **边界**：无需迁移 Qdrant；RRF 分数不是相似度或相关概率，不能沿用 cosine 阈值。官方默认参数有自己的排名约定，不应抄成普适常量。

### 7. RAGFlow：文档质量与可追溯引用

- **来源事实**：RAGFlow 公开提供文档解析、模板切分、分块可视化、可追溯引用以及多路召回和融合重排。[官方仓库](https://github.com/infiniflow/ragflow)
- **最小借鉴（设计建议）**：给 chunk 保留 document_id、标题、章节、版本和来源定位；前端展示实际使用片段，能够回答“这句话来自哪份 SOP”。先抽检原始文档到 chunk 的转换质量。
- **边界**：不必部署整套 RAGFlow；“有引用编号”不等于引用支持结论，需要核验引用存在性和蕴含关系。先解决文本 SOP，不扩张到复杂扫描件解析。

### 8. Lost in the Middle：上下文需要选择与预算

- **来源事实**：Liu 等在多文档问答、键值检索任务中发现相关信息的位置会影响表现，长上下文中部的信息可能更难被有效使用。[Lost in the Middle](https://arxiv.org/abs/2307.03172)
- **最小借鉴（设计建议）**：为短期消息、长期记忆、检索片段分别设置 token 预算；按相关性去重和截断，记录最终注入哪些证据；对相同问题比较 top-k 和上下文长度。
- **边界**：这是特定时期模型和任务的实验，不是对所有 2026 模型的固定性能判断，也不支持“上下文越短一定越好”。

### 9. MemGPT：分层管理上下文

- **来源事实**：MemGPT 借鉴操作系统分层存储，管理不同记忆层之间的信息迁移，在有限上下文中支持长文档与跨会话交互。[MemGPT: Towards LLMs as Operating Systems](https://arxiv.org/abs/2310.08560)
- **最小借鉴（设计建议）**：区分当前轮工作状态、会话消息/摘要、跨会话业务事实。只有相关长期事实进入当前 prompt；历史原文仍可追溯。
- **边界**：用 Redis、PostgreSQL、向量库各存一份数据不自动等于分层记忆。必须说明写入、晋升、召回、过期和纠错规则；无需复刻 OS 式中断机制。

### 10. Mem0：抽取、合并、检索记忆

- **来源事实**：Mem0 论文描述从持续对话中抽取、整合并检索显著信息，另有图记忆变体；其开源代码提供记忆管理实现。[论文](https://arxiv.org/abs/2504.19413)、[官方仓库](https://github.com/mem0ai/mem0)、[核心实现](https://raw.githubusercontent.com/mem0ai/mem0/main/mem0/memory/main.py)
- **最小借鉴（设计建议）**：只记明确确认的运营偏好和可引用业务事实，新增来源 message_id、实体、有效时间、状态；同一实体同一属性的新事实使旧值失效。拒绝把未经验证的助手回答写成业务真相。
- **边界**：不引入图数据库；论文中的评测优势仅对应作者实验。业务订单、套餐、工单等权威数据始终回查数据库，不依赖对话记忆覆盖。

### 11. Ragas：拆解 RAG 质量

- **来源事实**：Ragas 分别评估检索上下文、基于证据的生成和答案质量，论文提出无需完整人工参考答案的评估思路。[论文](https://arxiv.org/abs/2309.15217)、[官方仓库（原地址发生重定向）](https://github.com/vibrantlabsai/ragas)
- **最小借鉴（设计建议）**：先保留普通 Python 评测脚本，分开计算人工标注的 Recall@k、引用正确率，以及抽样人工校准过的 faithfulness judge；保存问题、检索片段、答案、模型版本与评分理由。
- **边界**：自动评分不是真值；不是所有指标都无需参考标注。改 prompt 的开发集与最终测试集分开，不能只报一个平均 Ragas 分数。

### 12. τ-bench：评执行结果与重复可靠性

- **来源事实**：τ-bench 将工具、领域规则和动态用户交互一起评测，比较最终数据库状态与目标状态，并提出 pass^k 衡量多次尝试的一致可靠性。[τ-bench](https://arxiv.org/abs/2406.12045)
- **最小借鉴（设计建议）**：本项目只提供分析建议，借鉴其“用可验证目标判断任务成功”的方法，校验必要事实、引用、工具参数和禁止断言；选一组核心场景重复运行，报告单次成功率与重复全部成功比例。当前不引入建跟进任务等外部写操作；若未来另立执行型场景，才需要数据库最终状态与写入幂等性校验。
- **边界**：pass^k 是重复都成功的可靠性视角，不能与“尝试 k 次至少一次成功”的 pass@k 混用。自建运营用例不能写成取得 τ-bench 官方成绩。

### 13. Langfuse：追踪—数据集—实验

- **来源事实**：Langfuse 提供 LLM/检索/Agent 动作追踪、prompt 管理、数据集以及代码、人工、LLM judge 评估接口。[官方仓库](https://github.com/langfuse/langfuse)
- **最小借鉴（设计建议）**：先统一 trace_id，记录每步 route、tool、retrieval、latency、token、error。把失败 trace 转为固定回归样本，保留已有日志栈；需要可视化时再接 Langfuse。
- **边界**：接入监控 SDK 不等于完成测评闭环；简历应能展示失败样本如何变成回归用例，以及优化前后同样本比较。

## 从来源到项目实验的最小清单（设计建议）

1. 意图：固定业务标签集 + 域外/歧义样本，比较当前路由与加澄清分支后的误接收率、完成率和调用次数。
2. 编排：同一复合任务比较当前执行方式、确定性分工和受控并行；统计完成率、关键事实缺漏、p50/p95 与 token。
3. RAG：现有向量检索 → 加词法融合 → 加重排，逐项消融，保持语料、问题和生成模型不变；分别看 Recall@k 与最终引用支持率。
4. 记忆：无长期记忆 → 全历史 → 有效事实召回；专测跨会话、事实更正、过期信息和不同用户隔离。
5. 全链路：以可验证目标状态判断完成；预设超时、空检索、工具异常、重复提交等场景。所有报告保留样本数、数据来源、版本、配置、失败案例与原始结果。

这些是为该业务构造的工程实验，不应被包装为论文复现、真实企业上线或未经验证的商业收益。

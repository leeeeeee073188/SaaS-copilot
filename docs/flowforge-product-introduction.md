# FlowForge Cloud 产品介绍与业务说明

版本：2026-09-10。产品定位：面向成长型企业的 API／Webhook 业务数据集成与运行管理平台。

本文完善项目的产品背景、客户场景、使用流程和服务规则。FlowForge 是虚构产品；客户名称、金额和使用量均为合成设计。文中区分“当前已实现”“当前模拟”和“规划”，完整产品叙事不等于完整功能已经交付。此前沙箱方案与本文有范围差异时，运行能力以代码及文末能力清单为准。

## 1. 产品是什么

FlowForge Cloud 帮助企业技术团队管理业务系统之间的 API 和 Webhook 接入，观察请求、用量与异常，并在同一个工作台管理团队权限、套餐和账单。

它围绕一个具体问题展开：**当业务数据需要在多个系统间传递时，团队如何知道连接是否正常、失败发生在哪里，以及下一步该怎么处理？**

例如，一家企业同时使用订单系统、CRM 和仓储系统。订单创建后，需要通知仓储系统履约；订单状态变化后，需要让 CRM 中的客户记录保持一致。开发者除了编写业务逻辑，还需要处理环境与凭证、请求失败、重复事件、接口限流和跨团队排障。

FlowForge 的完整产品设计是把接入配置、请求观察和协作管理放到统一平台。当前项目已落地其中的服务与管理闭环，并用固定集成记录模拟数据运行场景；尚未建设真实的数据转发或同步执行引擎。

EchoMind 是嵌入 FlowForge 的智能支持入口，帮助客户企业用户理解产品、定位接入问题、查询业务状态，并在权限允许时完成订阅变更或成员邀请。

### 可直接用于项目介绍的文案

> FlowForge Cloud 是面向成长型企业的业务数据集成与运行管理平台，围绕 API 和 Webhook 接入，提供集成观察、请求排障、用量权益、订阅账单与团队协作能力。内置的 EchoMind 智能助手结合产品知识与企业实时状态，为开发者、管理员和账单负责人提供有依据、可核验的服务支持。当前项目以有状态沙箱呈现核心服务流程，外部数据传输、支付和邮件投递采用模拟边界。

## 2. 谁购买、谁使用、谁受益

目标客户是存在多个业务系统、需要维护 API 集成，但不希望每次排障都跨多个后台找信息的成长型企业。是否适用主要取决于系统连接与协作复杂度，不以企业人数作为硬性门槛。

| 用户 | 典型职责 | 使用诉求 | 对应身份 |
|---|---|---|---|
| 企业技术负责人／组织所有者 | 决定接入方式、预算和团队安排 | 判断能力是否适合，控制成本和访问范围 | owner |
| 项目管理员 | 协调开发者和集成维护 | 查看集成异常、安排协作、邀请成员 | admin |
| 接入开发者 | 开发接口、验证环境、处理失败 | 查文档、请求记录、错误原因及配额 | developer |
| 财务或采购负责人 | 核对账单、管理订阅预算 | 解释金额、查看账期、了解变更何时生效 | billing_admin |

以上身份均属于**购买和使用 FlowForge 的客户企业**。FlowForge 提供商的内部客服不是当前主登录角色，也不能自动获得所有客户数据访问权。

## 3. 为什么需要这个产品

| 业务问题 | 客户受到的影响 | 产品应提供的帮助 |
|---|---|---|
| 测试配置误用于生产环境 | 接口报 401，上线验证受阻 | 明确集成环境、凭证标签和排查步骤 |
| 同样报 429，但原因不同 | 盲目重试，或误以为必须购买更贵套餐 | 联合查看错误原因、分钟限速和账期配额 |
| 技术和财务看到的信息不同 | “已经升级”与“仍被限制”的沟通反复 | 区分当前套餐、已预约套餐及生效时间 |
| 邀请成员后席位不足 | 管理员不理解未加入的人为何占席位 | 展示成员、待接受邀请和席位规则 |
| 文档与企业当前状态脱节 | 通用答案不能解释具体问题 | 公共知识解释规则，业务工具提供当前事实 |
| 重试一次操作产生重复效果 | 重复邀请、重复变更或对结果失去信任 | 幂等操作、明确回执及可追踪记录 |

业务价值应通过接入完成率、问题解决耗时、重复咨询和操作正确性验证；本文不假设已获得真实客户增长或效率收益。

## 4. 产品中的业务对象

```text
客户组织 Organization
├── 成员 Membership 与待接受邀请 Invitation
├── 项目 Customer project
│   └── 集成 Integration
│       ├── 所属环境 Environment
│       └── 脱敏请求记录 Request record
├── 订阅 Subscription → 当前套餐与预约变更
├── 用量 Usage 与当前权益 Entitlement
├── 账单 Invoice
└── 业务操作 Business operation 与操作回执 Operation receipt
```

- **组织**是合同、订阅和数据访问的归属范围。业务 ID 相同或项目名称相同，不构成跨组织访问依据。
- **项目**围绕一个接入目标组织资源，例如“订单履约通知”；当前代码只有项目引用，尚无独立项目管理页面。
- **集成**是某个来源或目标系统的连接配置，例如订单系统向履约系统发送 Webhook。当前仅展示固定集成元数据。
- **请求记录**描述一次请求的技术结果，如请求 ID、时间、HTTP 状态和原因码。HTTP 处理成功与下游业务完成是两个不同事实。
- **业务事件**表示订单创建、客户信息变更等业务事实；一个事件可能经历多次投递尝试。事件与投递模型属于下一阶段扩展，当前请求记录不能代替完整事件追踪。

## 5. 核心产品模块

### 5.1 产品能力与接入引导

用户首先需要判断：是否支持 API／Webhook、现有套餐能否承载请求规模、团队能加入多少人、出现问题时应提供哪些信息。

产品入口应按“了解能力 → 核对当前权益 → 查看接入方法 → 验证接入结果”组织。当前已有套餐目录、权益查询和简短知识文档；完整接入向导、可运行 SDK 示例和首次接入检查尚未实现。

推荐的新用户接入流程：

1. 确认当前组织、项目目标和本人权限。
2. 选择 API 或 Webhook 场景，明确数据来源与接收方。
3. 在测试环境核对凭证、参数和签名要求。
4. 发送测试事件，保存请求 ID，检查接收结果。
5. 切换生产配置，检查速率及配额是否满足预计负载。

第 2—5 步是完整产品的目标流程；当前只能通过模拟记录与知识说明演示其中的支持过程，不能实际完成传输验证。

### 5.2 API 与 Webhook 支持

排障需要组合三类信息：

- 用户提供的线索：集成编号、请求 ID、出现时间、预期结果与实际结果。
- 平台事实：集成环境、请求原因码、当前账期用量及有效权益。
- 产品规则：环境认证、权限、限流、幂等重试、Webhook 签名等说明。

当前工具可列出本企业集成、按集成查询脱敏请求记录、查询用量。知识库支持区分 `401 auth_environment_mismatch`、`429 rate_limit` 和 `429 quota_exhausted`。

对客户的回复应包括：已查到的事实、可能原因、下一步操作和仍缺少的证据。如果没有匹配记录，应说明无法确认；查到原因码也不能声称已经修复故障。

下一阶段最有价值的完善是：请求 ID 与时间窗口查询、完整参数文档、确定性的测试回放，以及修复前后两次结果对照。不是简单增加更多错误码文本。

### 5.3 用量与运行观察

客户需要分别理解：

- **账期配额**：一个账期允许消耗多少 API 请求。
- **分钟限速**：短时间内允许多快地发出请求。
- **日志保留期**：可以查询多长时间范围内的运行记录。

请求总量尚未用完，也可能触发分钟限流；日志查不到，也不代表请求从未发生。

当前实现包含用量快照、权益和固定故障记录。限速器、实时计量、日志生命周期清理均未实现。套餐中的速率与保留期是产品规则字段，不能据此宣称已有对应运行基础设施。

**下一阶段计量规则建议，尚未实施：**企业业务 API 的调用量与工作台、Agent 自身查询分开统计；认证通过且被受理的业务请求计入配额，认证拒绝和限流拒绝不计入配额；业务事件去重与 API 请求计量分别记录，不能因为复用事件 ID 就默认不消耗请求。上线前需要确定批量接口如何计数，并为各类请求编写计量验收用例。

### 5.4 订阅与账单

当前提供两个合成套餐：

| 权益 | Starter v1 | Growth v1 |
|---|---:|---:|
| 模拟月价 | ¥990 | ¥2,990 |
| 成员席位 | 5 | 20 |
| 每账期 API 请求配额 | 1,000,000 | 10,000,000 |
| 每分钟请求限制 | 60 | 300 |
| 日志保留规则 | 7 天 | 30 天 |
| API／Webhook 产品能力 | 支持 | 支持 |

金额采用 CNY，不模拟税务、折扣和汇率；价格不是市场报价。API／Webhook 为产品能力定义，当前只有支持沙箱，未实现真实传输引擎。

套餐变更的业务约定：

1. 用户先获得明确预览：当前与目标套餐、生效时间、当期增量费用、下周期价格。
2. 当前支持的当期增量费用为 0，变更在下周期生效。
3. 用户确认并提交后，状态为“已预约”；当期权益不立即变化。
4. 到期时再次检查目标套餐能否容纳成员和待接受邀请；不满足则保持原套餐，标记变更受阻。
5. 预览有效期为模拟时钟下的 15 分钟；资源版本变化后需重新预览。
6. 生成账单不等于支付成功。当前固定样本包含 paid/open 状态，周期推进生成 open 模拟账单，没有真实收款。

例如 Cedar 当前配额已耗尽，即使预约 Growth 成功，也不能告诉用户“现在已恢复调用”。真实产品通常还需要处理当期容量不足的路径，但当前加量包、立即升级和人工例外处理均未实现，应明确说明支持边界。

### 5.5 企业账户与协作

| 业务权限 | owner | admin | billing_admin | developer |
|---|---|---|---|---|
| 公共知识、当前权益和用量 | ✓ | ✓ | ✓ | ✓ |
| 本企业集成与请求详情 | ✓ | ✓ | — | ✓ |
| 本企业账单与订阅 | ✓ | — | ✓ | — |
| 预览和提交套餐变更 | ✓ | — | ✓ | — |
| 查看成员及邀请摘要 | ✓ | ✓ | ✓ | ✓ |
| 邀请 developer | ✓ | ✓ | — | — |

这里 admin 是协作和技术管理角色，并非账单管理员。邀请当前仅支持 developer，待接受邀请占用席位；新创建邀请有效期为 7 天。重复邀请同一待加入邮箱不重复占用席位，邀请创建不等于对方已经加入。

当前不发送真实邮件，未实现接受邀请、成员删除、角色调整、owner 转移、SSO 和 SCIM。固定种子邀请可以具有独立的到期时间，应以具体记录为准。

### 5.6 操作记录与用户信任

用户执行变更后应能回答三个问题：“是否受理了”“什么时候生效”“刷新或重试后结果是否一致”。

当前订阅和邀请操作通过业务服务写入状态，保存操作 ID、回执和成功审计。超时不等于失败，用户应先查原操作结果。Agent 的文字回复不是执行凭证，产品页面与操作回执才是核验入口。

当前审计主要覆盖成功业务写入；完整失败尝试审计、导出审计报表和长期保留策略属于后续扩展。

## 6. 三个具体客户场景

以下客户故事用于解释已有种子数据，不代表真实客户。数值描述的是初始场景；演示中的业务操作可能改变当前数据库，应通过工具重新读取。

### Aurora：订单系统上线接入

**客户背景：**虚构的电商运营企业，准备把订单事件接入履约系统。4 位成员使用 Starter，账期已用 80 万次请求。开发者在切换生产环境后遇到 401。

**已有事实：**`org_aurora`、`int_aurora`，记录原因是测试凭证与生产环境不匹配。

**服务过程：**开发者发起查询 → Agent 查询当前组织集成和脱敏记录 → 检索环境认证说明 → 建议检查环境与凭证配置，不要求粘贴完整密钥。

**进一步业务：**管理员邀请一位协作开发者；初始状态只有一个空席，成功后 pending 邀请占用最后一个席位。技术负责人可以预览 Growth，但升级不改变当前认证错误。

**验收：**不能把认证失败说成套餐不足；邀请不能超卖席位；不能把建议修改配置说成已经完成修复。

### Beacon：活动流量导致分钟限流

**客户背景：**虚构的营销运营企业，在活动开始时集中向 CRM 推送线索。使用 Growth，有 19 位成员和 1 个待接受邀请，账期已用 250 万次请求。

**已有事实：**`org_beacon`、`int_beacon`，429 原因为 `rate_limit`，账期配额并未耗尽；初始账单为 open。

**服务过程：**查看原因码、用量和当前速率规则 → 解释分钟限流与账期配额的区别 → 建议限速及退避策略。账单负责人查询时，解释 open 表示未标记支付完成，不能无依据推断已停服或自动扣款失败。

**进一步业务：**管理员再邀请成员应因席位不足失败；降级 Starter 也应因占用超过 5 席而失败。

**验收：**不把所有 429 都解释成流量包耗尽；不因存在未支付样本账单，就自行推断认证或限流原因。

### Cedar：账期配额耗尽与升级预期

**客户背景：**虚构的供应链协作企业，通过 API 接收业务状态，Starter 的 100 万次账期配额已经用完，5 个成员席位也已占满。

**已有事实：**`org_cedar`、`int_cedar`，429 原因为 `quota_exhausted`。

**服务过程：**检查当前用量和有效套餐 → 说明配额耗尽 → 展示下一周期 Growth 预览 → 用户确认后保存预约。

**客户关键追问：**“我已经升级，为什么还是不能调用？”

**正确解释：**已经预约下一周期变更，当期仍是 Starter；不能把预约成功解释成立即扩容。客户若需要当前周期恢复，当前沙箱应如实说明没有已实现的即时扩容路径。

**验收：**确认前不改订阅，确认后只改预约，到期才改有效套餐；状态与解释一致。

## 7. EchoMind 如何嵌入产品

EchoMind 的业务职责是理解用户问题，获取证据，提供下一步，并在授权范围内执行已有产品能力。普通页面和对话工具调用相同业务服务，确保结果一致。

| 用户诉求 | 知识依据 | 当前业务事实 | Agent 的交付物 |
|---|---|---|---|
| “Starter 能接 Webhook 吗？” | 版本化能力文档 | 套餐目录、本人权益 | 功能说明与接入边界 |
| “为什么接口报 429？” | 限流和配额规则 | 请求记录、用量、当前套餐 | 原因解释、证据与操作建议 |
| “下周期升级要多少钱？” | 生效和计价规则 | 当前订阅、目标套餐 | 具体预览，等待用户确认 |
| “邀请同事协作” | 角色和席位规则 | 当前成员、pending 邀请 | 有权限且席位足够时创建邀请并返回回执 |
| “刚才操作成功了吗？” | 状态说明 | 原操作回执 | 准确状态与生效时间 |

Agent 记忆适合保留对话进展、用户提供的接入背景和表达偏好；对账单、权限、用量等易变化事实，每次都应查询当前业务状态。

## 8. 产品体验建议

工作台的页面职责建议如下，其中前五项已有基础界面，后续能力按范围逐步补齐：

| 页面 | 当前内容 | 建议完善 |
|---|---|---|
| 概览 | 套餐、用量和权益 | 显示企业接入目标、关键异常摘要和清晰的首次使用入口 |
| API 集成 | 固定集成列表与请求记录 | 详情页、请求 ID／时间过滤、排障状态和测试结果 |
| 订阅账单 | 当前／预约套餐、预览、账单 | 明确有效时间、金额影响、预约原因和失败解释 |
| 企业账户 | 成员、邀请和新增邀请 | 剩余席位计算、邀请到期时间、接受与撤销流程 |
| 智能支持 | 对话、依据、操作卡 | 基于当前页面和所选集成生成问题入口，避免固定 Aurora 示例 |
| 接入指南（规划） | 暂无完整页面 | 认证、请求示例、签名、重试、错误语义和接入验证 |

信息层级应让用户先看到当前有效状态，再看到预约或历史状态。一个动作只展示一个明确结果，例如“已创建待接受邀请”，而不是笼统的“成员添加成功”。

## 9. 商业与服务边界

产品设计采用组织级月订阅，价格差异来自用量、速率、席位与日志保留规则。当前没有年付、超额自动计费、自助加量包、税务发票开具或真实付款能力。

功能咨询和排障知识支持所有客户成员，但私有账单、请求日志和写操作必须遵循角色权限。自动助手无法解决的问题，真实产品应提供人工支持渠道并携带已有诊断上下文；当前尚未接入真实工单和转人工系统。

平台不能保证修改建议执行后问题一定解决，也不能凭一次 HTTP 成功声称业务数据已经完整同步。可用性 SLA、数据地域、备份恢复和合规认证需要真实基础设施与制度支撑，本项目不虚构这些承诺。

## 10. 应如何衡量产品价值

| 指标 | 建议定义 | 当前可测程度 |
|---|---|---|
| 首次接入完成率 | 启动接入流程的组织中，完成首次验证的比例 | 需补真实或模拟验证链路 |
| 故障解决耗时 | 用户开始求助到验证恢复所需时间 | 当前仅能记录处理耗时，尚无修复闭环 |
| 诊断正确率 | 在有已知事实的场景中，原因与建议满足验收条件的比例 | 可扩展现有固定场景测评 |
| 自助解决率 | 无人工介入且验证解决的服务请求占比 | 当前无真实用户或人工交接数据 |
| 操作正确率 | 有权限且前置条件满足的操作是否产生预期状态 | 已有状态断言基础 |
| 越权／重复副作用 | 越权访问或同一意图重试造成额外变更的次数 | 已有隔离、幂等和并发席位测试 |
| 单次解决成本 | 模型、工具及人工介入成本之和 | 尚未建立完整成本统计 |

已有 60 个参数化用例通过只能证明对应离线业务链路，不是上述所有产品指标已达标。

## 11. 当前能力对照与最小后续建设

| 能力 | 当前状态 |
|---|---|
| 组织、会话、角色校验和数据隔离 | 已实现；登录是演示身份选择，非生产认证 |
| 套餐、用量、成员和账单查询 | 已实现，数据为合成业务状态 |
| 订阅预览、确认、预约、到期切换和模拟账单 | 已实现；到期由测试时钟驱动 |
| 邀请、席位检查、去重、到期处理和操作审计 | 已实现；无真实邮件和接受邀请流程 |
| 集成元数据、请求错误与用量样本 | 当前模拟；每个组织一个集成和一条初始请求记录 |
| 真实 API 接入、Webhook 转发与事件处理 | 规划 |
| 请求窗口过滤、验证回放和修复复测 | 规划 |
| 凭证管理、SSO、SCIM、真实支付与工单交接 | 规划 |

为满足“代码改动尽可能小、业务足够可深挖”，建议按以下顺序补充产品，而不是直接建设完整集成平台：

1. **接入文档与运行证据**：先定义少量真实可执行的沙箱 API，增加查询过滤和可验证示例，让 API 支持具有可检查的事实。
2. **可重复的排障闭环**：建立请求失败、配置调整、测试重放、结果恢复的局部流程；测试控制接口不能由 Agent 随意调用来改变答案。
3. **完整邀请生命周期**：补邀请接受、撤销与席位释放，保持权限和幂等约束一致。
4. **体验与测评连接**：基于当前组织生成上下文示例，记录问题解决与业务状态结果，再评估模型效果和成本。

这些是后续建设建议，不是本次已执行的代码变更。本文主要补齐了产品定位、客户故事、规则、交互和验收口径。

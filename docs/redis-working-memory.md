# Redis 工作记忆与高并发方案

## 已实现

业务记录和操作审计继续存 SQLite，工作记忆固定存 Redis，知识、历史片段与偏好存 ChromaDB。
不再创建或读写 SQLite conversations 表，也不在 Redis 失败时隐式切换存储。
旧表保留，运行 `python -m saas.migrate_memory` 可复制旧会话到 Redis：SET NX 防止覆盖已有会话，TTL 为 24 小时。
迁移前暂停旧进程接收聊天，避免迁移时仍有 SQLite 写入；迁移完成后启动新版本。

Redis 键含业务数据库路径的命名空间哈希和组织、用户、会话的范围哈希。
同一业务数据库路径的多个进程共享工作记忆；不同演示库及测试库隔离。
正式多机器部署需要统一明确的应用命名空间，而不能依赖各机器的本地路径。
迁移工具处理旧 SQLite 历史；更早版本无命名空间的 Redis 键不自动导入。

工作历史继续使用 JSON 字符串，减少与原有格式的改动。追加采用 WATCH → GET → MULTI → SETEX → EXEC：
读取后若其他客户端修改键，则重读并合并，最多重试 8 次，带随机退避。
连接池上限 32、连接和命令超时 2 秒；没有全局会话写锁，不同会话不必串行。
启动时检查 Redis，运行期 /ready 检查 Redis 可用性。

超过 16 条消息时先向 Chroma 归档，再把工作记忆缩减到最近 8 条。
归档使用稳定 ID；失败不提交 Redis 裁剪。竞争失败可能留下重复覆盖范围的历史片段，但不会覆盖并发已提交的工作消息。
Redis 与 Chroma 不存在跨库事务；超过重试上限会明确失败。EXEC 后断连可能导致结果未知，不自动重放业务操作。
24 小时 TTL 随工作记忆写入刷新；TTL 过期不触发归档，历史片段仍有 4000 字符截断限制。

Docker Compose 增加独立 Redis，宿主机端口 6380、容器内 6379，使用 AOF、数据卷和 noeviction。
这是本地单节点配置，不是高可用部署；noeviction 达到内存上限后会拒绝写入。

## 面试：如何优化高并发

先区分“很多用户同时请求”和“同一会话同时发送多条消息”。目前已解决并发保存的覆盖问题，
尚未保证同会话整轮读取历史、推理、写回的顺序，也没有通过高 QPS 压测证明吞吐能力。

| 瓶颈 | 当前状态 | 后续实现方案 |
|---|---|---|
| 请求排队与模型限额 | 进程内 Semaphore(4)，总超时 90 秒 | 有界入队，满载返回 429/503；按组织配额与模型 RPM/TPM 限流，重试加抖动 |
| 同会话一致性 | Redis CAS 防止保存覆盖 | conversation_id 分区串行队列；或带租约、续约及 fencing token 的锁覆盖整轮，明确超时与锁丢失行为 |
| Agent 实例锁 | 同角色仍串行，防止实例级轨迹串扰 | 将工具轨迹移到请求局部变量，使用共享异步模型客户端和受限并发；不要无上限创建 Agent |
| SQLite 写竞争 | 读操作也进入 BEGIN IMMEDIATE，进程内业务锁 | 先缩短事务、拆读写，评估 WAL；写负载增长后迁移 PostgreSQL，保留唯一约束、版本校验、幂等与回执 |
| 归档和检索 | 本地 Chroma、归档位于同步请求链路 | 后台归档队列与幂等任务，确认归档后裁剪；独立向量服务和有界检索线程池 |
| 横向扩容 | SQLite、本地 Chroma、进程内指标 | 共享业务数据库和向量服务，Redis 高可用，统一命名空间；指标按实例抓取或配置多进程采集 |

不能仅增加 Uvicorn worker 就宣称横向扩容完成：当前实例锁、SQLite 单写者、Chroma 本地目录以及进程内指标都需要处理。
WAL 改善读写共存，但并不让 SQLite 同时拥有多个写入者。

## 验证方式

先做 1/4/8/16 并发阶梯测试，分别覆盖不同会话和同一会话，再逐步增加负载。
记录端到端与排队 p50/p95/p99、吞吐、超时、429、模型 Token、Redis CAS 重试及 SQLite 锁等待。
校验消息成对完整、权限隔离、每个操作只有一个回执、金额和席位约束；吞吐提升不能靠丢消息或重复执行换取。
分别运行固定延迟 fake provider（测服务端开销）和真实模型（测限额与外部延迟），不混用结果。

可用面试表述：我先把业务事实与短期上下文分开存储，通过 Redis CAS 防止并发写覆盖；
进一步扩容时优先处理同会话顺序、Agent 锁和模型配额，再迁移关系型数据库及向量服务，最后用分层压测验证。

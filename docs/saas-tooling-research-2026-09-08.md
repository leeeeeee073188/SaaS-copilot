# B2B SaaS 工具执行与业务沙箱调研

调研日期：2026-09-08。本文为新增工程方案的依据，**不代表 EchoMind 已实现相关能力，也不代表已接入以下产品**。目标是用小规模、有状态的模拟 SaaS 支撑功能咨询、API 对接、订阅账单、企业账户四类任务，并使结果可验证。真实支付、邮件发送和企业身份服务不在本轮实施范围。

## 1. 核心结论

模拟产品应同时提供版本化知识、确定性业务状态和可执行工具。知识库回答规则，业务 API 返回当前事实，写工具产生受约束的状态变化，评测检查变化是否正确。只生成产品说明与成功响应无法验证权限、重复提交、变更生效时间和故障恢复。

下面区分“来源机制”与“最小借鉴”。后者均为本项目设计建议，不是外部产品原样规定。

## 2. 九组关键一手资料

### S1：Stripe 订阅变更预览与按比例计费

**来源机制：**Stripe 允许在不修改订阅的情况下预览账单；价格和数量变更可能产生按比例费用。预览与执行采用同一个 `proration_date` 可避免时间推进造成计算差异。[Stripe：Prorations](https://docs.stripe.com/billing/subscriptions/prorations)

**最小借鉴：**为套餐或席位变更提供 `preview_subscription_change`，返回原值、新值、差额、生效时间与 `preview_id`。确认后执行 `apply_subscription_change`，引用预览快照，不能重新让模型计算价格。预览绑定租户、操作者、参数摘要、订阅版本与有效期；版本变化后要求重新预览。

**范围边界：**最终 MVP 仅实现月付、单币种、整数分计价的下周期变更，当期差额为 0；按剩余周期计算模拟差额作为二期选项。不做真实扣费，不宣称完整复刻 Stripe 的税务、优惠和所有计费模式。

### S2：Stripe 幂等请求

**来源机制：**Stripe 通过幂等键保存首次执行的状态码和响应，重试复用结果；同一键与不同参数搭配会报错。校验失败或并发冲突等未开始执行的请求有不同的保存语义。[Stripe：Idempotent requests](https://docs.stripe.com/api/idempotent_requests)

**最小借鉴：**沙箱持久化 `(tenant_id, tool_name, idempotency_key, arguments_hash, result)`；状态更新、审计事件、幂等记录在同一 SQLite 事务提交。应用层生成并在重试时复用键。模拟“已提交但响应丢失”，验证重试只产生一次订阅变更、一次账单调整或一次邀请。

**范围边界：**不必复制 Stripe 的缓存期限和所有失败语义，但必须清晰定义哪些失败可重试、同键异参如何处理；幂等不等于权限许可。

### S3：Stripe Test Clocks / Simulations

**来源机制：**Stripe 的模拟利用 test clocks 控制时间，检验订阅升级、试用、生命周期 Webhook 等变化。[Stripe：Use Simulations](https://docs.stripe.com/billing/testing/test-clocks)

**最小借鉴：**数据集固定 `scenario_now`，所有到期、账期与预览有效性从注入时钟读取。开发控制台或评测入口可推进时间，复现“本周期取消、期末生效”等场景。初始化 fixture 后，每次运行从独立副本开始。

**范围边界：**时间推进和场景重置属于评测管理接口，不暴露为客户 Agent 常规业务工具。优先采用本地时钟，无需依赖 Stripe 账户或网络。

### S4：Lago 的套餐、用量与权益模型

**来源机制：**Lago 是开源计量与账单系统；计划组织定价、账期、功能权益等配置，客户通过订阅关联计划，用量计费关联 billable metrics。[Lago 开源仓库](https://github.com/getlago/lago)、[Lago：Plan overview](https://getlago.com/docs/guide/plans/overview)

**最小借鉴：**建立一份套餐定义，驱动功能矩阵、权益查询、API 配额检查与模拟费用规则。最终初版选用两档套餐、API 请求量指标和明确席位上限。用户问“为什么 API 返回 429”时，可以同时查询分钟级限流原因、账期用量和套餐权益，再检索限流文档。

**范围边界：**借鉴领域划分，不引入 Lago 整套服务。不将平台所有定价能力变成简历项目范围；账单金额仍由确定性代码计算。套餐表、文档和场景数据共享版本来源，避免三个地方各写一套价格。

### S5：Keycloak Organizations

**来源机制：**Keycloak 用组织表示 B2B 客户或伙伴，支持成员管理、邀请、身份代理，以及将组织信息映射到令牌供应用授权使用。[Keycloak：Managing organizations](https://www.keycloak.org/docs/latest/server_admin/index.html#_managing_organizations)

**最小借鉴：**沙箱主体采用 `org_id + actor_id + membership + role`，org 即本项目的 tenant 范围。最终初版采用 owner/admin/developer/billing_admin 四种自定义角色，分别约束成员邀请、集成诊断、账单操作。查询资源、写资源和记忆读写都必须匹配当前可信组织上下文；不能根据用户一句“我是管理员”改变身份。

**范围边界：**演示身份从后端白名单会话注入，前端角色切换明确属于沙箱模拟；它不是生产身份认证。暂不部署 Keycloak，也不声称已经实现 SSO、SCIM 或企业级认证。

### S6：MCP 工具发现与调用

**来源机制：**MCP 定义 `tools/list`、`tools/call`、工具名称和输入/输出 Schema；规范建议保留用户拒绝调用的能力，并指出不可信服务提供的工具注解不能被直接信任。[MCP 2025-11-25：Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

**最小借鉴：**优先改造现有本地注册表，显式记录业务域、读写属性、所需权限、超时及参数 Schema。模型只能选择已注册工具。工具描述用于选择，实际权限由执行器校验；写操作结果携带状态版本和审计 ID。

**范围边界：**上述是本地工具治理。只有实现标准传输、初始化、发现及调用，并由独立客户端完成互通测试后，才能在简历写“标准 MCP 接入”。MCP 注解、模型返回的 `confirmed=true` 都不能充当业务授权凭据。

### S7：MCP 授权边界

**来源机制：**MCP 授权规范处理 HTTP 传输层访问，要求服务器验证令牌的目标受众，禁止把其他服务令牌直接透传充当 MCP 凭据；STDIO 的凭据处理不同。[MCP 2025-11-25：Authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization)

**最小借鉴：**区分三层：身份是否可信、角色是否允许操作、用户是否授权此次具体变更。即使以后接入 MCP，后端仍需做租户隔离、资源归属和业务权限检查。审批记录绑定预览、操作者及参数，执行时重新验证。

**范围边界：**本地沙箱无需先建设 OAuth 平台；也不能将提示词中的权限规则当成后端隔离机制。当前文档参考固定的 2025-11-25 规范，实施标准 MCP 时应重新核对目标版本。

### S8：τ²-Bench 论文

**来源机制：**τ²-Bench 将用户和 Agent 放在共享环境中，双方均可通过工具改变状态，从而评估协作任务。[τ²-Bench 原始论文，2025](https://arxiv.org/abs/2506.07982)

**最小借鉴：**为 API 对接设计需要用户配合的多轮任务：Agent 查诊断和手册，用户模拟修正接收端配置，Agent 再次检查投递记录。任务应有初始状态、业务政策、用户目标和结束条件，而非只判断答案像不像参考文本。

**范围边界：**初版可用确定性脚本模拟用户动作；暂不接入完整基准框架，也不声称本地 SaaS 分数等同于官方 τ²-Bench 成绩。

### S9：τ-Bench 当前评测实现与版本变化

**来源机制：**调研日 `tau2-bench` 仓库首页已介绍 τ³。当前评测文档说明，参考 `actions` 常用于在新环境中生成目标数据库状态；默认的数据库状态评测不要求 Agent 严格复刻参考调用顺序。[官方仓库](https://github.com/sierra-research/tau2-bench)、[Task Schema and Evaluation](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md)

**最小借鉴：**本地成功条件采用“关键业务状态正确 + 必须告知的信息完整 + 无禁止副作用”。例如订阅席位增加成功，要求新席位数、模拟账单差额正确、只提交一次，并向用户告知生效时间；仅回答“已完成”不得通过。权限不足任务要求相关业务状态保持不变，同时解释原因。

**范围边界：**本项目宜显式断言目标字段和不变量，忽略审计时间戳等合理差异，不必机械比较整个数据库哈希。评测数据、执行器、政策和模型版本都应固定；禁止将动态 `main` 当作历史 τ² 的固定复现版本。

## 3. 建议落地顺序与验收证据

| 顺序 | 最小交付 | 直接验证的 Agent 能力 |
|---|---|---|
| 1 | 两档套餐、三个组织、受信模拟身份、SQLite 状态与固定时钟 | 咨询引用与事实查询是否一致，是否跨租户泄漏 |
| 2 | 四域只读工具；API 请求/投递日志支持关联查询 | 路由是否选对业务工具，RAG 是否检索对版本 |
| 3 | 订阅变更预览/执行、模拟成员邀请两条写闭环 | 多轮补参、权限校验、确认绑定、幂等与状态更新 |
| 4 | 故障注入和独立 fixture 副本；状态断言评测 | 超时重试、重复提交、过期预览、越权及误修改 |
| 5 | 按需补标准 MCP 适配或更多业务工具 | 注册扩展是否复用治理能力，而非复制编排逻辑 |

验收最少保留四类证据：原始多轮轨迹、工具参数与结构化返回、业务状态前后差异、自动断言结果。以上是建议的验证方式，不能提前写成已经取得的性能指标。
